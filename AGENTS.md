## Project Structure

- `src/pages/` — file-based routes (`.astro`, `.md`, or `.ts` for endpoints). Most pages have `export const prerender = true`.
- `src/pages/api/contact.ts` — the only request-time route (Zod → Turnstile verify → Resend notify + confirm).
- `src/pages/**/*.md.ts` — markdown twin of every URL; `src/pages/llms.txt.ts` is the index for AI agents.
- `src/content/projects/` — Markdown source for the `projects` content collection (Zod-validated at build).
- `src/layouts/` — shared layouts wrapping page slots.
- `src/components/` — reusable Astro components (organize by feature folder when groups emerge).
- `src/assets/logos/` — brand assets vendored from `github.com/auditmos/branding`.
- `src/styles/globals.css` — Tailwind v4 entry (`@import "tailwindcss";`) + `@theme` block with brand tokens.
- `src/env.d.ts` — declares `App.Locals` typed against Cloudflare `Env`.
- `worker-configuration.d.ts` — auto-generated by `pnpm cf-typegen`, never edit. Gitignored, not committed: `pnpm install` regenerates it via the `prepare` script, so a fresh clone gets one before the first typecheck. Its contents vary with your local `.dev.vars`, which is why committing it produced churn.
- Path alias `@/*` → `src/*`.

## Architecture

Prefer **deep modules** (Ousterhout): small interface hiding large implementation. Test at module boundaries, not internals. See `.claude/rules/deep-modules.md`.

Technology-specific rules live in `.claude/rules/`. Activate automatically when touching relevant files — `frontend/astro.md`, `frontend/tailwind-v4.md`, `api/astro-endpoints.md`, `api/cloudflare-workers.md`, `cloudflare-deployment.md`, `error-handling.md`, `atomic-imports.md`, `general.md`.

### Project-specific conventions

- **Static-first:** every page sets `export const prerender = true` except `src/pages/api/contact.ts`, `src/pages/api/csp-report.ts` (a report-only policy with nowhere to report cannot be validated before it is enforced, and a prerendered asset cannot read a POST body), `src/pages/mcp.ts`, and the two OAuth routes (`src/pages/oauth/register.ts`, `src/pages/oauth/token.ts` — issuing a credential is a cryptographic exchange over a POST body, which a prerendered asset cannot perform). Don't introduce new request-time routes without a reason documented in the PRD. Page routes pass *through* the Worker (see markdown negotiation below) but are still served from their prerendered asset — that is a routing hop, not a render, and it must stay that way.
- **Agent-readiness regressions:** `pnpm agents:verify [url]` scans a deployed host and diffs the result against `REQUIRED_CHECKS` in `scripts/agents-verify-lib.ts` — the checks backed by something this site actually ships. Most scanner checks fail by design (OAuth discovery, A2A, WebMCP are not implemented), so a raw pass count means nothing; only the declared set is enforced. Run it after deploying. When you implement a new agent surface, add its check to `REQUIRED_CHECKS` — the script reports newly-passing checks as `NEW PASS` precisely so the list does not drift behind reality.
- **Markdown negotiation:** `Accept: text/markdown` on a page URL returns that page's markdown twin (`src/site/markdown-negotiation.ts`, wrapped around the adapter handler by `src/worker.ts`, which is `main` in wrangler.jsonc). It only works because `assets.run_worker_first` lists the page routes — otherwise the asset server answers first and the Worker never sees the request. **Adding a page means adding *both* its URL forms to `run_worker_first`** — `/about` and `/about/`, because those patterns match the path literally and the bare form does not claim the slash form (`src/site/run-worker-first.ts` encodes exactly what a pattern claims). A wildcard entry like `/work/*` spans both and needs no second line. Build-output tests fail when either form is missing. Both representations send `Vary: Accept`, so don't strip it — a shared cache would start handing markdown to browsers. `pnpm dev` never runs the Worker entry or the asset router, so negotiation always returns HTML there — verify with `pnpm preview`, which does.
- **Slash-free canonical URLs:** `/about`, never `/about/`. Three things enforce it and must move together — `trailingSlash: "never"` (astro.config.mjs, drives dev-server routing), `assets.html_handling: "drop-trailing-slash"` (wrangler.jsonc, makes the asset server serve the bare form instead of redirecting to the slash form), and `canonicalRedirect()` (`src/site/canonical-url.ts`, first thing in `src/worker.ts`). The third exists because the second only governs requests the *asset server* answers, and `run_worker_first` claims every page route before it: `/work/<slug>/` used to answer 200 with the page body, a second reachable URL for the same document. The Worker 301s any trailing-slash URL to its canonical form for GET/HEAD, leaving other methods alone so a 301 cannot rewrite a POST to `/api/contact` or `/mcp` into a GET. Changing one alone reintroduces a redirect hop on every internal link or a duplicate URL; build-output tests assert all three. **The third only fires for paths `run_worker_first` claims**, and those patterns match literally: `/about/` used to answer `html_handling`'s 307 instead, because only `/about` was listed — a temporary redirect consolidates no ranking signals, which is the entire point of the 301 (#38). Both forms are listed now. A build-output test asserts that, and `pnpm agents:verify` re-checks it against a deployed host, because the failure lives in whether Cloudflare's asset router reaches the Worker at all — a fact no build artifact describes and `pnpm dev` never exercises.
- **MD-mirror:** a single page-enumerator helper is the source of truth for `*.md.ts` endpoints and `/llms.txt`. Adding a new route extends both surfaces — a CI test asserts coverage.
- **MCP rate limit:** `/mcp` is unauthenticated, so it is rate limited by the `MCP_RATE_LIMITER` binding (wrangler.jsonc, `period` accepts only 10 or 60). `MCP_RATE_LIMIT` in `src/mcp/server.ts` is the single source for the number: the endpoint enforces it, `initialize` reports it to clients, and `/agents.json` publishes it. Change the constant and the binding together — a test asserts the advertised limit matches the constant, but nothing can catch the binding drifting from it. Note the limiter is *permissive and eventually consistent* by design: each isolate checks a locally cached counter, so an instantaneous concurrent burst can exceed the limit before counts propagate, and it is per Cloudflare location rather than global. It bounds sustained abuse, which is the actual threat here; it is not a hard quota. Verify it with sustained sequential requests — a parallel burst will show no 429s and look like a broken limiter. `/api/csp-report` is limited the same way (`CSP_REPORT_RATE_LIMITER`, `CSP_REPORT_RATE_LIMIT` in `src/csp/report-handler.ts`) and carries the same caveat: change the constant and the binding together.
- **Content Security Policy:** `src/site/content-security-policy.ts` owns the whole policy and the mode. It ships **report-only** — flip `CSP_MODE` to `"enforce"` once the sink has been quiet through a week of production traffic (#30). One header name serves both delivery surfaces on purpose: `_headers` covers everything the asset server answers, `withSecurityHeaders()` fills the policy in on what the Worker renders itself, and it *fills in rather than sets* — overwriting a page's own policy would drop the script hashes and refuse every inline block. **Inline-script hashes are derived from the emitted HTML** by `agentDiscoveryHeaders()`, never written down: a stale hash fails closed, so a build-output test asserts every inline script in `dist/` has a matching one. Adding an inline `<script>` needs no action; adding a *third-party* origin, or a new inline `style` source, means editing the directives here. JSON-LD is deliberately unhashed (a data block is never CSP-checked), and `style-src` keeps `'unsafe-inline'` because Shiki writes colours into `style` attributes, which hashes cannot govern. Watch for violations with `pnpm csp:violations` — it filters `wrangler tail` down to the `csp_violation` warnings and summarises on exit, but it streams **live**, so a quiet run only proves its own window was quiet; query Workers Logs for the period as a whole. Violations post to `/api/csp-report` via `report-uri` — not `report-to`, which needs an absolute URL a static build cannot know per environment, and which Chrome would let silently supersede `report-uri`.
- **Agent-discovery headers:** the `agentDiscoveryHeaders()` integration (`src/site/discovery-headers.ts`) generates the `_headers` file after the build, advertising `/llms.txt` and each page's `.md` twin as RFC 8288 `Link` relations. It appends to what `@astrojs/cloudflare` already wrote, so it must stay *after* the adapter in `integrations`. Don't hand-write `public/_headers` for these — add the link there instead.
- **Redirects:** static ones are declared in `astro.config.mjs`. `public/_redirects` is the exception and is hand-written on purpose — the Cloudflare adapter *appends* its generated rules to that file rather than replacing it, so hand-written rules stay first and win, and a wildcard (`/projects/* → /work/:splat`) can only live there: a dynamic destination declared in the config gets resolved to the file backing it (`/work/:slug/index.html`), which is not the canonical URL and 404s for the `.md` twins. Unlike `_headers`, this file is safe to edit.
- **Rendered Markdown:** `src/styles/prose.css` styles `<Content />` output and is imported by the page that renders it, not by `globals.css` — the homepage renders no Markdown and has the least headroom under the transfer budget. Import it from any future Markdown-rendering page. Fenced blocks take their background from the Shiki theme (`markdown.shikiConfig` in astro.config.mjs), because Shiki inlines that colour and no rule here can outrank it.
- **Projects schema:** the `client` field is a discriminated union — either `{ name, url? }` (public/named) or `{ sector }` (anonymised NDA work). Exactly one variant required.
- **Article import:** `pnpm import-article` maps an externally authored launch article (the `content-launch` skill's `article.md`) onto that schema. Title, slug, summary and tags come from the article's own frontmatter — the prompts only cover year, client and industry, and every prompt has a flag so the import can run non-interactively. The leading H1 is stripped because `/work/<slug>` renders the title and summary itself.
- **Contact endpoint atomicity:** `/api/contact` returns 200 only when *both* emails (notification + confirmation) dispatched successfully. Partial sends → 502 with structured log.
- **OSS aggregator:** must never fail the build. On GitHub API failure, fall back to cached file, then to empty list.
- **Local Worker runtime — use `pnpm preview`, not `wrangler dev`:** not a style preference. Two miniflare majors live in this tree, both transitive and neither pinnable: the build runs miniflare 4 (via `@cloudflare/vite-plugin` ← `@astrojs/cloudflare`), `wrangler dev` runs miniflare 5-alpha. They disagree about the `SENTRY_DO` schema, so sharing a persist root made `pnpm build` — and therefore `pnpm deploy`, `deploy:staging` and `deploy:production` — fail with `table _cf_ALARM has 3 columns but 2 values were supplied` until `.wrangler/state` was deleted by hand *and* every orphaned `workerd` killed. `persistState` in astro.config.mjs now gives the build its own root (`src/site/miniflare-state.ts`), so the two cannot collide; a contract test fails if that wiring is dropped. `pnpm preview` goes through the same miniflare the build does, which is why it was always the right tool for verifying Worker behaviour.

## Cloudflare runtime

Access bindings through `import { env } from "cloudflare:workers"` — this is the only supported pattern in Astro v6 + `@astrojs/cloudflare` v13 (the old `Astro.locals.runtime.env` was removed). `env` is typed against `worker-configuration.d.ts`. After editing `wrangler.jsonc` bindings, run `pnpm cf-typegen`.

`wrangler.jsonc` ships with three env blocks (`dev`, `staging`, `production`) — each gets its own Worker name. Deploy a specific env with `pnpm deploy:<env>` (staging → `staging.auditmos.com`, production → `auditmos.com`). Full runbook incl. the one-time Turnstile/Resend setup and the cutover from the legacy `auditmos-web` Worker: [`docs/deployment.md`](./docs/deployment.md).

Per-env contact vars live in `.dev.vars` / `.dev.vars.staging` / `.dev.vars.production` locally (never committed). This matches the wrangler convention — `.dev.vars.<env>` is loaded ahead of `.dev.vars` when `CLOUDFLARE_ENV=<env>` is set. Required for the contact form: `TURNSTILE_SITE_KEY` (public widget key), `RESEND_API_KEY`, `TURNSTILE_SECRET_KEY`, `CONTACT_TO_EMAIL`. Required for OAuth: `OAUTH_SIGNING_KEY` — cryptographically random and **distinct per environment**, since it derives every client secret and signs every access token (a shared key would let a staging credential authenticate against production). Optional: `GITHUB_TOKEN` for the OSS aggregator's build-time rate limit.

<important if="you are writing or modifying tests">
- Tests live next to source as `*.test.ts`, mirrored name (`foo.ts` ↔ `foo.test.ts`)
- Vitest with globals enabled — no need to import `describe` / `it` / `expect`
- Globals are typed via `"vitest/globals"` in `tsconfig.json` (`types` array)
- Path alias `@` resolves to `src/`
- `src/pages/**` excluded from test discovery — extract endpoint logic into a `src/lib/` or `src/<domain>/` module and test that instead
- **Test only the module's public boundary** (exported functions), not internals — see `.claude/rules/deep-modules.md`
- **Pure functions only** in unit tests. For code that touches fs / network / process, extract a pure helper and test it; cover the side-effecting orchestrator with a separate integration test (none ship by default)
- Reference: `scripts/init-project-lib.test.ts` shows the convention — `describe` per exported function, `it.each` for parametric cases
- **Asserting against build output:** call `buildSite()` from `src/site/build-output.ts` in `beforeAll`. It runs `astro build` *once per test run* behind an on-disk lock (`src/site/build-once.ts`), because vitest runs suites in parallel isolated workers and `astro build` empties `dist/` before writing it — two unsynchronised builds leave every build-output suite intermittently reading a directory the other just wiped. `vitest.global-setup.ts` clears that state at the start of each run (and on each watch re-run) and deliberately never builds, so filtering to an unrelated file still costs nothing. Every suite that reads `dist/` asserts `buildRunCount() === 1`, so a regression here fails loudly instead of going flaky.
</important>
